# Building the SDK

The SDK is generated by the firmware build, from the firmware's own
headers, so it always matches the firmware it is built with.

## The generator

The generator (`tools/generate_native_sdk/generate_pebble_native_sdk_files.py`)
runs automatically as part of the firmware build (normal variant only — PRF
and test builds skip it). It exports the white-listed functions, `typedef`s
and `#define`s from the firmware tree and produces the files needed to build
native watchapps, all under `build/`:

- `build/sdk/<abi>/include/pebble.h` — typedefs, defines and function
  prototypes for apps (plus `pebble_worker.h` for background workers and a
  few version/fonts headers). Exported declarations are copied verbatim and
  use `pbl/kernel/compiler.h` macros rather than raw `__attribute__`; the
  generator rewrites those into their GCC spellings, so the SDK ships no
  firmware headers. Only macros that alias an attribute or forward their
  arguments to a builtin can be exported.
- `build/sdk/<abi>/lib/libpebble.a` — static library containing
  trampolines that call the exported functions in flash, or Xtensa import
  symbols that the loader resolves directly to those functions
- `build/pebble/pebble.auto.c` — `g_pbl_system_tbl`, the table of function
  pointers the trampolines use to find an exported function's address;
  compiled into the firmware image

Every board with the same ABI generates the same headers and library.
The ABIs are `armv7m`, `riscv32` for xteinkx4, and `xtensa` for xteinkx4pro. The few defines that differ between platforms, such as
`PBL_IF_COLOR_ELSE` and `PBL_PLATFORM_TYPE_CURRENT`, are decided in the
header by the defines the app build passes for the platform it builds for
(`PBL_COLOR`, `PBL_PLATFORM_EMERY`, ...), see {doc}`exporting`. The generator
checks that this gives the build's platform what its firmware has.

## Packaging

The rest of the distribution is packaged by the firmware build's `sdk`
target, which fills in the same `build/sdk/` tree:

```shell
pbl configure --board $BOARD
pbl build sdk
```

`tools/cmake/sdk.py` copies the common files from `sdk/` into
`build/sdk/common/` — the app project templates under `sdk/defaults/`, and
the tools and resource pipeline the app build shares with the firmware —
and the CMake package apps are built with, `sdk/cmake/`, into
`build/sdk/cmake/` ({doc}`app_build`). It also bundles `sdk/waftools/` into
the deprecated `waf` binary older projects build with. That waf is the only
one left in the tree: everything it needs lives under `sdk/`, and it is
built out of tree, so packaging leaves the checkout untouched.

It also writes `build/sdk/<platform>/platform.json`, the description of the
platform out of the build's Kconfig. The SDK has no other record of what
its platforms are like: the app build derives the `PBL_*` defines, resource
tags and size limits of each platform from that file. An SDK put together
from several firmware builds needs the `platform.json` of each, and nothing
else of them: a platform's directory needs no headers and no library.

The app build takes the headers and the library from the platform's own
directory if it has them, and from the directory of its ABI otherwise. The
frozen platforms have their own, as their headers stop at the SDK revision
they were frozen at. For tools that only look in a platform's directory,
`include` and `lib` there are links to those of the ABI.

## The whole SDK

A released SDK holds every platform. {doc}`../pbl/sdk` builds it:

```shell
pbl sdk $VERSION --frozen $FROZEN --tarball
```

Each platform is packaged from one board, listed in `sdk/boards.yml`. For
each of them the command configures a build of the SDK shell firmware and builds two targets:

- `sdk`, as above;
- `sdk_emulator`, on boards that run in QEMU, which adds what the `pebble`
  tool emulates the platform with to `build/sdk/<platform>/qemu/`: the
  firmware, the SPI flash image with the system resources, and the timeline
  layouts.

The headers and the library of the ABI have to come out the same from every
board, and the command stops if they do not. It then adds the frozen platforms, whose headers `tools/build_sdk.py`
generates at the SDK revision each was frozen at, and whose `libpebble.a`
and emulator come from the directory given with `--frozen`, as they are the
ones those platforms were frozen with. The result is `build-sdk/sdk-core/`:

```
sdk-core/
  manifest.json            version and requirements, for the pebble tool
  package.json, requirements.txt, use_requirements.json
  pebble/
    cmake/, common/, waf   what the platforms share
    armv7m/, riscv32/      include/, lib/: what the platforms of each ABI share
    <platform>/            platform.json, qemu/, links to include/ and lib/
    <frozen platform>/     include/, lib/, qemu/
```

Both app builds read `package.json` through `sdk/tools/pebble_project.py`;
the CMake build's steps are `sdk/tools/pebble_build.py`.

## Xteink X4 Pro native apps

For a new X4 Pro app, build the native `xteinkx4pro` variant. It runs
directly on the Xtensa LX7 and supports the hardware touchscreen. Existing
Flint ARM apps run through Samsa on normal X4 Pro firmware. To export the native SDK separately
from the stock watch SDK, install Espressif's ESP32-S3 GCC toolchain and the
usual ARM GCC app toolchain, then run this in the PebbleOS checkout with its
Python development environment active:

```shell
pbl sdk 4.47-xteink --board xteink_x4_pro --tarball -b build-sdk-pro
export PEBBLE_SDK="$PWD/build-sdk-pro/sdk-core/pebble"
```

The package contains `xtensa/lib/libpebble.a` and
`xteinkx4pro/platform.json`. This board describes a 240×400 monochrome
touch display. The emulator and Picco share its ABI but lack a touchscreen
driver. For the hardware SDK, export from `xteink_x4_pro`.

In an external CMake app, use the project layout in {doc}`app_build` and
include `"xteinkx4pro"` in `pebble.targetPlatforms` in `package.json`.
Build the native PBW with:

```shell
cmake -S /path/to/app -B build-app -G Ninja -DPEBBLE_PLATFORMS=xteinkx4pro
cmake --build build-app
```

From the firmware checkout, install the PBW over a USB console by passing
its serial device explicitly. The normal firmware must be running with
the console Pebble protocol enabled. Close other clients of that port first.

```shell
python tools/install_xteink_pbw.py --port /dev/cu.usbmodemEXAMPLE build-app/my-app.pbw
```

To install on Espressif's QEMU, put its `qemu-system-xtensa` on `PATH`
or set `PEBBLE_QEMU_ESP32S3_BIN` to the executable. Start the firmware in
one terminal, then install from a second terminal using the same TCP port:

```shell
pbl configure --board qemu_esp32s3 -b build-pro-qemu
pbl build -b build-pro-qemu
pbl run -b build-pro-qemu --console-port 12345
```

```shell
python tools/install_xteink_pbw.py --port socket://127.0.0.1:12345 build-app/my-app.pbw
```

### Ship a native and ARM variant together

To support both the Pro and Flint from one codebase, list `"xteinkx4pro"`
and `"flint"` in `pebble.targetPlatforms`. Export both toolchains' platform
files and build the app in a fresh directory.

```shell
pbl sdk 4.47-xteink --board xteink_x4_pro --board qemu_flint -b build-sdk-dual
export PEBBLE_SDK="$PWD/build-sdk-dual/sdk-core/pebble"
cmake -S /path/to/app -B build-app-dual -G Ninja '-DPEBBLE_PLATFORMS=xteinkx4pro;flint'
cmake --build build-app-dual
```

The resulting PBW contains a native binary under `xteinkx4pro/` and an ARM
binary under `flint/` with the same app UUID. The X4 Pro console installer
and CoreApp with X4 Pro support select the native binary first. Older phone
software that recognizes Flint can select the ARM binary, which the Pro
runs through Samsa. Keep each binary in its own architecture's directory.


For a legacy phone that presents the original X4 as Flint, make a separate
reader-specific PBW from the native RISC-V variant. The output targets the
original X4. A stock Flint requires ARM code.

```shell
python3 tools/pbw_as_platform.py app.pbw app-x4-legacy-phone.pbw
```
